# Jotang Note 概要设计（MVP）

> **类设计、方法签名、SQL 明细以代码为权威**（建表脚本 `src/main/resources/schema.sql`，接口出入参见 Apifox，§9），本文档不重复。

## 0. 设计决策

| 编号 | 决策点 | 结论 | 影响 |
|---|---|---|---|
| D1 | 退出/改密后的 token 失效 | 不做服务端即时失效，用 2h 短 TTL 缓解；前端删 token 即退出 | 暂不引入 Redis |
| D2 | 下载量口径 | **近似**计数 | 计数可能偏高 |
| D3 | 登录限频维度 | **仅账号维度**：5 次失败锁 10 分钟 | 避免误伤同校园网出口的整批用户 |
| D4 | 笔记删除 | **软删除**：`note.status` 扩为 `ONLINE/OFFLINE/DELETED`，行不物理删除 | 收藏占位可渲染；外键永不悬空 |
| D5 | 标签关联 | 新增 `note_tag` 关联表 | |
| D6 | 密码找回令牌 | **落库** `password_reset_token`（SHA-256 哈希、一次性消费、TTL 30min） | 应用重启不失效；暂不引入 Redis |
| D7 | 头像访问 | 头像存**独立公共读 Bucket**（公共读 / 私有写），接口返回完整公网 URL | 免签名、浏览器直连；与笔记私有 Bucket 隔离 |
| D8 | 学院归属 | 学院独立成表；`user.college_id` **必填**，`course` **去掉** `college` 列。笔记的学院 = **上传者的学院**，`note` 不冗余存、靠 JOIN `user` 推导 | 上传表单只需选课程；改学院**回溯改变**全部历史笔记归属；**不做按院隔离** |
| D9 | AI 摘要范围 | 只做「用户点按 → 读附件 → 生成摘要填入简介框」：**光栅图走多模态、md / txt 走纯文本调用**（§5.8）、同步一次性 JSON、用户可改且**不自动保存**、结果**不落库** | 新增 `ai` 模块；PDF / Office 仍需先抽文本，列为 V2 |
| D10 | 重置邮件投递 | **引入 RabbitMQ**：请求链路只「写令牌 + 投消息」，发信由消费者做；**事务提交后**投递；1 次初始 + 3 次重试（2s/4s/8s），耗尽进死信队列（TTL 1h）。由 `jotang.mail.mode` 切换，默认 `smtp` | 动机是**防枚举**而非性能；新增 `mail` 模块与 Broker。代价：Broker 是新单点、明文令牌也进 Broker |

表数：**9 张**。

### 1.1 分层与模块

  S --> MAI --> LLM

- **模块边界**：Controller 只做参数校验与编排；业务规则全部落在 Service；跨表/复杂检索走 MyBatis XML，单表 CRUD 走 MyBatis-Plus。
- **跨模块访问**：跨模块的**业务操作**走对方 Service。**但检索侧的多表 JOIN 不受此限**——列表 / 搜索 / 详情都需匹配课程名 / 标签名 / 上传者，`NoteMapper.xml` 可直接 JOIN `course`、`tag`、`user`、`college`。
- **跨模块写对方单表列**：仅当对方没有能承接该写的 Service、或注入它会形成构造器循环依赖时，允许直接注入对方 Mapper，**且必须在类注释写明理由**。
- **鉴权**：`common` 内的无状态 JWT 过滤器统一拦截，`admin` 模块通过角色规则保护。

### 1.2 部署拓扑

```mermaid

    MQ[("RabbitMQ 4<br/>重置邮件队列 + 死信队列")]
  end
  OSS[("阿里云 OSS 私有 Bucket<br/>笔记文件")]
  OSSA[("阿里云 OSS 公共读 Bucket<br/>头像")]
  H5 -->|HTTPS| NG
  NG -->|/api| APP
  APP --> MySQL
  APP -->|jotang.mail.mode=queue 时投递 / 消费| MQ
  APP --> TMP
  APP -->|内网 Endpoint 流式上传| OSS
  APP -.->|签发签名 URL · 浏览器直连公网| OSS
  APP -->|内网 Endpoint 写头像| OSSA
  H5 -.->|公网直连读头像| OSSA
```

- **RabbitMQ 单机**（`docker compose` 起 `rabbitmq:4-management`）
- **OSS 两个访问面**：ECS 与 OSS 同 Region，后端上传 / 写头像一律走 `oss-<region>-internal.aliyuncs.com`；签发给浏览器的签名 URL 与头像公网直读走公网 Endpoint。**二者必须是两个客户端**——签名 URL 的主机名取自签发时所用客户端的 Endpoint。
- 「用哪个 Endpoint」是**环境差异而非代码差异**：本机开发数据面也走公网，由 `application-local.yaml` 覆写。
- **两个 Bucket**：笔记文件→私有；头像→公共读。
- 开发期可先用 IP 访问，但 JWT/密码为明文传输，仅限自测。

## 3. 数据库设计

统一约定：`InnoDB` + `utf8mb4`；主键 `BIGINT UNSIGNED` 自增；时间字段 `DATETIME`；**文本一律存原文，输出时转义**。

### 3.1 表清单（10 张）

- **账号**：`user` · `college` · `password_reset_token`
- **内容**：`note` · `note_file` · `course` · `tag` · `note_tag`
- **互动**：`favorite`
- **AI**：`ai_message`

### 3.2 表结构要点

**建表脚本以 `src/main/resources/schema.sql` 为唯一权威**，本节只记**读列定义读不出来的约束**。库表变更的迁移流程见 §7.4。

| 表 | 关键约束 | 要点 |
|---|---|---|
| `college` | `uk_name` | 预置数据，应用内只读；注册时必选（D8） |
| `user` | `uk_username`、`uk_email`；`college_id` **NOT NULL** + `fk_user_college` | `avatar` 存**对象键**而非完整 URL（§6.7）；`status` 预留，MVP 不实现禁用 |
| `course` | `uk_name`；`is_other` | 预置数据 + 一条固定的「其他」；D8 后**不含 `college` 列** |
| `note` | `fk_note_uploader`、`fk_note_course`；`status` 三值；**`updated_at` 无 `ON UPDATE`**；6 个索引 | 软删除，行不物理删除（D4）；`deleted_at` 仅在 `status=DELETED` 时写入 |
| `note_file` | `uk_note_id`（一份笔记一个文件）、`uk_storage_key` | `storage_key` 格式 `notes/yyyy/MM/{uuid}.{ext}`；`is_purged=1` 表示对象已物理清理（§3.3） |
| `tag` | `uk_name` | 目录侧唯一写路径：上传时按名复用或当场创建 |
| `note_tag` | 复合主键 `(note_id, tag_id)` | **无顺序列**，读取按 `tag.id` 升序（§5.4） |
| `favorite` | `uk_user_note` | 重复收藏由它兜底（40902）；`note_id` 指向软删除的 `note`，外键永不悬空 |
| `password_reset_token` | `uk_token_hash`；`used_at IS NULL` 为一次性判据 | 只存 `SHA-256(令牌)`；`expires_at` = 签发 + 30 分钟（§6.6） |
| `ai_message` | `fk_am_user`；`idx_conversation` | 一轮问答两行（USER / ASSISTANT）。**`conversation_id` 是全库唯一非 `BIGINT` 的主键类型**（`CHAR(36)` 的 UUID），因为它不对应任何一张实体表——本轮不做会话列表，没有值得单开一张表的会话元数据 |

**`note` 的六个索引**（§8.2 的三种排序都走这些索引，删掉任一个都会让对应排序退化成 filesort）：

| 索引 | 支撑 |
|---|---|
| `idx_status_created` (`status`, `created_at`) | 最新发布 |
| `idx_status_updated` (`status`, `updated_at`) | 最近更新，`sort=latest` 的排序键 |
| `idx_status_view` (`status`, `view_count`) | 热门·浏览 |
| `idx_status_download` (`status`, `download_count`) | 热门·下载 |
| `idx_course_status` (`course_id`, `status`) | 课程页 |
| `idx_uploader_status` (`uploader_id`, `status`) | 我的上传 |

### 3.3 设计要点

- **软删除闭环**：`note` 行永不物理删除 → 收藏列表能读到 `DELETED` 渲染"笔记已删除"、读到 `OFFLINE` 渲染"已下架"，外键不悬空。**无需**在 `favorite` 里存标题快照。
- **计数并发**：`view_count/download_count/favorite_count` 一律 `UPDATE note SET x = x + 1 WHERE id = ?` 原子自增；收藏重复性由 `uk_user_note` 兜底（40902）。
- **`note.updated_at` 语义 = 用户最后编辑笔记的时间**，只有编辑接口显式写 `updated_at = NOW()`，浏览量自增、下架/恢复一律不碰它。
- **计数器一致性**：`favorite_count` 为派生值，提供一条离线校准 SQL（`UPDATE note SET favorite_count = (SELECT COUNT(*) FROM favorite WHERE note_id = note.id)`）用于对账，不进入主链路。
- **搜索策略**：MVP 用 `LIKE '%kw%'` 覆盖标题/简介/教师/课程名/标签，**接受全表扫描**，分页深度最多 50 页 / 前 1000 条；预留 `FULLTEXT ... WITH PARSER ngram` 作 V2 开关。
- **OSS 物理清理**：用户删除笔记后清理 OSS 对象并置 `note_file.is_purged=1`，**不可恢复**；管理员的下架/恢复只改 `status`，不动对象。
- **密码找回令牌**：只存 `SHA-256(令牌)`，明文仅出现在邮件链接；`used_at IS NULL` 为一次性判据；重新申请即作废全部未用令牌。详见 §6.6。
- **头像对象键版本化**：`avatars/{userId}/{uuid}.{ext}`，换头像即换键，旧键不覆盖 → 可对公共读 Bucket 配长 `max-age` 强缓存而不串图。详见 §6.7。
- **学院归属**：学院挂 `user` 而非 `course`。改学院会回溯改变该用户全部历史笔记的归属；上传表单只需选课程；笔记不做按院隔离。

## 4. 状态机

### 4.1 笔记状态（`note.status`）

```mermaid
stateDiagram-v2
  [*] --> ONLINE: 上传成功
  ONLINE --> OFFLINE: 管理员下架
  OFFLINE --> ONLINE: 管理员恢复
  ONLINE --> DELETED: 上传者删除
  OFFLINE --> DELETED: 上传者删除
  DELETED --> [*]
```

| 状态 | 列表/搜索 | 详情页 | 预览/下载/收藏 | 编辑 | 我的上传 | 收藏列表 |
|---|---|---|---|---|---|---|
| ONLINE | 可见 | 正常 | 允许 | 允许 | 正常 | 正常 |
| OFFLINE | 不可见 | **本人 / 管理员可看**，他人 40301 | 禁止 | **允许**（改完仍是下架） | 可见并标注 | 占位"已下架" |
| DELETED | 不可见 | **40301（所有人）** | 禁止 | 禁止 | **不可见** | 占位"已删除" |

- **恢复**只允许 `OFFLINE → ONLINE`；`DELETED` 是终态，无出边。
- 状态迁移合法性集中在 `NoteStateMachine` 判（`requireTransition(from, to)`，表驱动覆盖四条边）。

### 4.2 用户角色

`USER` / `ADMIN` 二值，存 `user.role`，签发时写入 JWT claim。
**MVP 无后台、无自助提权**，管理员账号只能预先造好。

## 5. 接口设计

统一前缀 `/api`，统一响应体 `{ "code": 0, "message": "ok", "data": ... }`；鉴权走 `Authorization: Bearer <jwt>`。完整出入参与示例同步至 Apifox。

### 5.1 认证

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/auth/register` | 注册（用户名/邮箱/密码/学院）；学院取自 `GET /api/colleges`，必填 |
| POST | `/api/auth/login` | 登录，成功返回 JWT + 用户信息 |
| POST | `/api/auth/logout` | 退出（前端清 token；服务端空实现） |
| GET | `/api/auth/me` | 当前登录用户 |
| POST | `/api/auth/password/forgot` | 发送重置邮件（邮箱维度限频；响应不区分邮箱是否存在） |
| POST | `/api/auth/password/reset` | 凭邮件令牌重置密码（一次性、TTL 30 分钟） |

### 5.2 用户与资料

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/users/{id}` | 个人主页（昵称/学院/`avatarUrl`/上传数） |
| PUT | `/api/users/me` | 改昵称 / 改学院，**PUT 全量替换**（两字段都必填）。出参 `ApiResponse<UserInfo>` |
| POST | `/api/users/me/avatar` | 上传头像（≤2MB，仅 jpg/png/webp，写公共读 Bucket）。出参 `ApiResponse<UserInfo>` |

**`POST /api/users/me/avatar`**——multipart 单文件，只写 `user.avatar` 一列：

- **出参回显整个 `UserInfo`**：头像是服务端生成的对象键，前端推不出 URL。
- **旧头像对象不删**，清理挂在 §7.3。

### 5.3 课程与标签

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/colleges` | 学院列表（注册表单与筛选的下拉数据源） |
| GET | `/api/courses` | 课程列表，支持按名称搜索 |
| GET | `/api/tags` | 标签列表 |

### 5.4 笔记

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/notes` | 上传（multipart：文件 + 元数据） |
| GET | `/api/notes` | 。**只出 ONLINE**；超深分页报 40001 |
| GET | `/api/notes/search` | 关键词搜索（标题/简介/教师/课程名/标签） |
| GET | `/api/notes/{id}` | 详情。`isFavorited` 查 `favorite` 表 |
| PUT | `/api/notes/{id}` | 编辑元数据（上传者本人，JSON 而非 multipart） |
| DELETE | `/api/notes/{id}` | 软删除（上传者本人，`→DELETED`）。`OFFLINE` 亦可删 |
| GET | `/api/notes/{id}/preview-url` | 图片预览：返回 OSS 签名 URL |
| GET | `/api/notes/{id}/raw` | MD/文本预览：后端代理返回原文 |
| GET | `/api/notes/{id}/download` | 返回下载签名 URL，`download_count+1`（近似口径） |
| GET | `/api/users/me/notes` | 我的上传，按上传时间倒序分页。**只出 ONLINE / OFFLINE；不含 `uploader` |

> 列表 / 搜索 / 详情 / 收藏等只要展示上传者信息，一律返回 **`avatarUrl`**（完整公网 URL），前端直接 `<img src>`，无需二次请求签名或代理。

- **非 ONLINE 时 `file` 整体为 `null`**，其余元数据一条不少。**这条现在只在「本人 / 管理员看一篇已下架的笔记」这一种情形下可见**。

- 前端不需要为 `DELETED` 写分支。
- `status` 与 `previewMode` 按**枚举名**输出（`"ONLINE"` / `"IMAGE_INLINE"`）；`createdAt` / `updatedAt` 是 ISO-8601 无时区串。

**列表响应体**（`PageResponse<NoteListItemResponse>`）——外壳固定 `items` / `total` / `page` / `size`；`total` 是**真实总数不封顶**。列表项比详情少 `status` / `summary` / `teacher` / `createdAt` / `file`。

- **列表只出 ONLINE**，`total` 同样是筛过的数。
- 列表项带 `isFavorited`。

**`PUT /api/notes/{id}`**——只改元数据与标签，不碰 `note_file`：

- **请求体是 JSON 而非 multipart**（编辑不能增删附件）。
- **回显复用 `GET /api/notes/{id}`**。
- **该不该显示编辑按钮由前端判断**。
- **边界**：`OFFLINE` 放行、`DELETED` 报 40301；非本人 40300、id 不存在 40400。
- **状态门用普通比较判 `DELETED`，暂不走 `NoteStateMachine`**。

**我的上传**（`GET /api/users/me/notes`）：

- **只出 `ONLINE` 与 `OFFLINE`，`DELETED` 无条件排除**。
- **带 `status`**，这正是不复用 `NoteListItemResponse` 的原因。
- **不含 `uploader`**（恒等于当前登录用户）

### 5.5 收藏

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/notes/{id}/favorite` | 收藏。仅 ONLINE（否则 40301）；重复 40902；笔记不存在 40400。出参 `{favoriteCount}` |
| DELETE | `/api/notes/{id}/favorite` | 取消收藏。**幂等**：没收藏过也回 200 与当前计数，只有笔记不存在才是 40400。**非 ONLINE 也放行**。 |
| GET | `/api/users/me/favorites` | 我的收藏，分页 `page`/`size`，按**收藏时间倒序**，含占位项。 |

### 5.6 管理员

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/admin/notes/{id}/offline` | 下架（`ONLINE→OFFLINE`）。**幂等**：已是 `OFFLINE` 返回 200 且不写库；已删除报 40301、不存在报 40400。 |
| POST | `/api/admin/notes/{id}/online` | 恢复（`OFFLINE→ONLINE`）。规则与下架对称。**不能复活已删除的笔记** |

- 需 `role=ADMIN`；详情页对管理员显示"下架/恢复"按钮，前端依据 JWT 的 role 判断。管理员用的是普通用户的详情接口
- **只改 `status` 一列，不动 OSS 对象，也不碰 `updated_at`**。

### 5.7 统一错误码

| code | 含义 | HTTP |
|---|---|---|
| 0 | 成功 | 200 |
| 40001 | 参数校验失败（`data` 携带字段级明细 `[{field, message}]`） | 400 |
| 40100 | 未登录 / token 无效或过期 | 401 |
| 40101 | 用户名或密码错误（登录表单内提示，**不跳转**） | 401 |
| 40300 | 无权限（非本人 / 非管理员） | 403 |
| 40301 | 笔记已下架或已删除。**五点用法各有各的口径**：**详情**对非本人 / 非管理员的 `OFFLINE` 与对所有人的 `DELETED`；**预览 / 下载 / 收藏**对所有非 `ONLINE`；**编辑**只在 `DELETED` 上用它（`OFFLINE` 放行）。见 §4.1、§5.4 | 403 |
| 40400 | 资源不存在 | 404 |
| 40901 | 用户名已被占用 | 409 |
| 40902 | 重复收藏 | 409 |
| 40903 | 邮箱已被注册 | 409 |
| 42200 | 文件类型 / 大小不合法（含摘要的正文超长）。上传准入（§6.1）与预览的模式校验（§6.2）共用 | 422 |
| 42300 | 账号已锁定（`data` 携带剩余锁定秒数） | 423 |
| 42900 | 摘要生成过于频繁（按用户限频，§6.8） | 429 |
| 50000 | 服务器内部错误 | 500 |
| 50300 | AI 摘要服务暂不可用（模型超时 / 上游失败，§6.8） | 503 |

> HTTP 状态码供传输层分流，业务码供应用层精确分支。同一 HTTP 状态可承载多个业务码（如 `40300` / `40301` 同为 403），前端据此区分，无需解析 `message` 文案。

### 5.8 AI 辅助摘要

> 本节编号排在错误码之后是**刻意的**：重编号会把那些引用全部指错。

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/ai/summary` | **上传场景**。multipart，字段 `file`，可选 `title` / `teacher` 作上下文 |
| POST | `/api/ai/summary/notes/{noteId}` | **编辑场景**。文件已在 OSS，服务端自取。`DELETED` 报 40301、`OFFLINE` 放行；id 不存在 40400 |

出参统一为 `{"code":0,"message":"ok","data":{"summary":"..."}}`。

- **两个接口的差别是文件位置**：上传时对象还不存在（文件只在前端手里），编辑时对象已在 OSS。
- **支持的附件分两档**：光栅图（jpg / jpeg / png / gif / webp）以 base64 进多模态输入；`md` / `txt` 按 UTF-8 解成正文、原样进纯文本调用，不剥 Markdown 语法。其余类型（含 pdf / Office）报 42200。
- **正文超限直接拒**（42200），不截断：按 code point 计上限 2 万字，另有一道字节预筛防堆（§6.1）。
- **`summary` 是建议不是结果**：接口**不写任何库表**，存不存由随后的 `POST /api/notes` 或 `PUT /api/notes/{id}` 决定。

### 5.9 AI 对话

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/ai/chat` | 一问一答。`message` ≤ 2000 字符；可选 `conversationId`，留空即开一段新会话 |

出参 `{"code":0,"message":"ok","data":{"reply":"…","conversationId":"…"}}`。

- **`conversationId` 由服务端生成并回显**，前端续聊时原样带回。
- **消息落 `ai_message`，一轮两行（USER / ASSISTANT）**。
- **历史全量重发且不裁剪**
- **模型可调用工具**：按标题精确检索在线笔记、读某篇笔记的附件正文。
- **按用户限频，超出报 `42900`**，额度与摘要**各自独立**。

- **Spring AI 2.0.1 跑在 Boot 4.0.8 上是降级运行**：编译通过、上下文能起、全量测试通过，**当前可用**；但 HTTP 客户端在真实调用下的行为（超时、重试、异常映射）**尚未验证**。两条路：保持现状，或把 Boot 升到 4.1.1 对齐（影响全项目）。
- **AI 对话的工具调用只由手工验证过，自动化测试覆盖不到**（§6.9）。工具执行发生在框架的 `ToolCallingAdvisor` 里，而测试里整条 `ChatClient` 是 mock，那个 advisor 不在链上。手工打真实 API 已确认模型会调工具、结果能回灌、Spring AI 生成的 schema（含 `$schema` / `additionalProperties: false` / `strict: false`）DeepSeek 端点照单全收。**待实测后钉死的是**：prompt 措辞在边界情形下的效果、§7.1 里那几个上限（尤其是对话限频 `30 次 / 小时`），以及真实时延与费用。
- **AI 摘要没有结果缓存**。要做需先有「附件内容 → 摘要」的键（内容哈希列或按 `storage_key` 做键），上传场景因还没有 id 只能落在编辑场景。
- ~~**补偿删除留下的孤儿对象，对账扫不到**（无数据库行即无从发现）。~~ **已解决**（笔记上传与换头像两处）：`jotang.purge.mode=queue` 时补偿删除会把这条待办投进 MQ，重试耗尽落死信队列、由深度巡检报出来。**残余**：投递那一刻 Broker 也不可用的话，仍然只剩一行日志——要彻底堵住得把「删不掉的 key」也落库（tombstone 表），本轮没做（《功能说明：笔记上传》§2.5）。
- **旧头像清理仍缺一个前置件**（§7.3）：`StorageService` 没有 `list`，加它是一次需单独拍板的接口扩张。**本轮没做。**
- **`password_reset_token` 的过期行清理尚未落地**：`@EnableScheduling` 已就位，挪进来只是加一个定时方法。要么做，要么明确接受过期行长期堆积。
- **死信队列的监控只做了一半**。三个层次：最低是定时打日志报队列深度；中间是 `/actuator/health` 的 `HealthIndicator`（本项目**尚未引入 Actuator**）；最高是接告警通道。**孤儿对象那条死信队列已做最低一档**（`OrphanObjectDlqMonitor`，非 0 打 WARN）——不做的话投 MQ 的收益就是空的（§7.3）。**重置邮件那条仍是一件都没做**：它的 DLQ 非空同样需要人看，但目前只有管理台能看见。
- **发布确认（publisher confirm）没有开**：`convertAndSend` 返回只代表「写进了 socket」。要真知道得开 `publisher-confirm-type=correlated` + `ConfirmCallback`，但**绝不能在请求链路上等它**（会把 §6.6 刚消掉的耗时差搬回来），只能做成异步打日志。
- **`/raw` 破了前端的响应信封约定**，前端那一刀要处理：`frontend/src/api/http.ts` 的响应拦截器假定响应体恒为 `{code,message,data}`，读到 `/raw` 的成功响应时会因 `body.code === undefined` 判成失败（`ApiError`）。两条路：绕开该实例另发一个带 `Authorization` 头的请求，或让拦截器按 `Content-Type` 分流。`/raw` 的**失败**响应仍是 JSON 信封，可照常分流。
- **`/raw` 对 HEAD 请求会白白读一遍对象**：`@GetMapping` 同时匹配 HEAD，处理器照常打开 OSS 并拷贝整份内容，只是容器把 body 丢弃。
